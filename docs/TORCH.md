# Клуб «Факел» (ARG-54)

Комьюнити выпускников экспедиции: участник, прошедший экспедицию
(`users.graduated_at`, см. [SURVEY.md](SURVEY.md)), теряет Динамику и задания и
упирается в пустоту — «Факел» даёт причину продолжать пользоваться платформой.

**Гейт — постоянный ручной тумблер**, не биллинговый. Изначальный документ
«Продуктовая модель: экспедиция и клуб (v1)» предполагал гейт «активная подписка
+ `graduated_at`»; по итогам обсуждения с пользователем (2026-09-27) решено
иначе — `users.torch_unlocked` включает/выключает только админ, независимо от
тарифа/подписки участника. Подписка и её сценарии (ARG-32) в этот гейт не
входят вовсе.

## Видимость пункта меню

Пункт «Факел» в боковом меню:

- полностью **скрыт**, пока `graduated_at IS NULL` (и роль не `admin`);
- **виден** выпустившемуся участнику независимо от `torch_unlocked` — тумблер
  решает не видимость пункта, а то, что внутри (заглушка или чат);
- виден админу всегда, даже без собственного `graduated_at`.

Правило вычисляется на клиенте из полей `/api/auth/me` (`role`, `graduated_at`) —
как и остальные пункты меню в этом проекте, отдельного `/menu`-эндпоинта нет
(см. `useAccessContext` в `frontend/src/features/app/RequireAccess.tsx`).

## Что видит выпустившийся

- **`torch_unlocked = false`** — заглушка: один общий текст на всех закрытых
  (не персонализированный), редактируемый админом. Отдаётся `GET /api/torch/stub`
  (`app/api/torch.py`) — доступен любому, кому виден пункт меню (тот же признак:
  `role == 'admin' or graduated_at is not None`).
- **`torch_unlocked = true`** — попадает в раздел «Факел»: **свой список чатов**,
  отдельный от Рубки (не таб внутри неё, см. «Раздел, а не таб» ниже) — общий
  чат клуба + личные и групповые чаты, которые участники заводят друг с другом
  и с админами внутри самого раздела.

## Раздел, а не таб внутри Рубки

Первая версия ARG-54 просто резолвила «/torch» в конкретную комнату Рубки
(`/chats/{room_id}`) — по факту это была ссылка на один чат внутри общего
интерфейса Рубки, а не отдельное место. По итогам обсуждения с пользователем
(2026-09-27, тот же день, что и решение про ручной гейт) это признано багом
восприятия: «Факел» — самостоятельный раздел со своей лентой чатов, который не
должен путаться со старыми чатами экспедиции.

- `rooms.torch_scope` (BOOLEAN, expand-only) — маркер «эта комната относится к
  разделу «Факел»»: ставится и на singleton-чат клуба (`is_torch`), и на любые
  dm/группы, созданные внутри раздела. **Разделение списков — целиком клиентское**
  (`frontend/src/features/chat/RoomList.tsx`): Рубка (`tab='chats'`) фильтрует
  `torch_scope` комнаты ИЗ своего списка, «Факел» (`tab='torch'`) — фильтрует
  ИМЕННО их. `GET /api/rooms` как отдавал все комнаты одним списком, так и
  отдаёт — `torch_scope` просто ещё одно поле `RoomOut`, как `is_news`.
- `frontend/src/features/chat/ChatLayout.tsx`/`RoomList.tsx` переиспользуются для
  всех трёх лент (`tab: 'chats' | 'channels' | 'torch'`) — у «Факела» нет
  переключателя Чаты/Дневники (это не под-таб Рубки), но есть те же кнопки
  «Новый чат»/«Группа», просто с другим источником контактов (см. ниже) и без
  привязки к `can_create_groups`/`graduated_at` — право уже проверено гейтом
  раздела (`withTorchGate` в `routes.tsx`).
- Пункт меню «Факел» в наве стоит **над** «Рубкой» (`routes.tsx`, порядок массива
  = порядок пунктов) — по прямому пожеланию пользователя: раздел «текущий»,
  Рубка — архив прошедшей экспедиции.

## Комната клуба и dm/группы внутри раздела

- `rooms.is_torch = true` — **singleton на всю платформу**, не на поток
  (в отличие от `rooms.is_news`, который с ARG-104 стал уникальным ПО ПОТОКУ).
  Партиционирования по `intake_id` нет намеренно: выпускники разных потоков
  оказываются в одном сообществе. Уникальность страхует частичный индекс
  `uq_rooms_torch_singleton` (`WHERE is_torch`) — гонка при создании ловится
  через `IntegrityError`, тот же приём, что у `ensure_news_channel`. `is_torch`
  остаётся узким маркером «эта самая singleton-комната», `torch_scope` — широким
  «относится к разделу» (ставится на обе сразу, см. выше).
- Создаётся лениво `ensure_torch_room` (`app/services/rooms.py`) — вызывается
  из app-lifespan (гарантированно существует уже на старте, `created_by` =
  первый найденный админ) и из `grant_torch_access`/`revoke_torch_access` на
  случай, если lifespan ещё не успел её завести.
- Тип singleton-комнаты — обычный `group`, group-семантика ROOMS.md (пишет
  любой член), НЕ channel (там пишут только админы).
- **Членство в singleton-комнате серверное, не self-service**: участника
  добавляет/убирает только `grant_torch_access`/`revoke_torch_access`
  (`app/services/torch.py`), вызываемые из админ-эндпоинтов — не через обычный
  `add_member`/`remove_member`. Выключение тумблера **удаляет** строку
  `room_members` целиком (не soft-delete — soft delete в проекте применяется к
  контенту, не к членству); история сообщений не трогается.
- **Dm/группы, заведённые ВНУТРИ раздела, наоборот, self-service** — обычный
  путь `POST /api/rooms`/`POST /api/rooms/{id}/members`, просто с флагом
  `torch=true` в теле (`CreateRoomRequest.torch`, `app/schemas/room.py`) —
  результат получает `torch_scope=True`. Круг видимости приглашаемого другой
  (см. ниже), но сам механизм создания/членства — тот же, что у обычной
  Рубки, ничего заново не изобретали.

## Круг видимости контактов внутри «Факела»

Обычный ранговый каскад тарифов (`contact_visible`/`cohort_plan_ranks`,
ARG-110, [ROOMS.md](ROOMS.md)) после выпуска не при делах — у выпускника
тариф формально мог остаться (историческое поле), но принимать по нему решения
о «Факеле» бессмысленно. Поэтому:

- **`GET /api/torch/contacts`** (`app/api/torch.py`) — параллельный, НЕ более
  узкий вариант `GET /api/users/contacts`: любой другой `torch_unlocked=true`
  участник + **любой** админ (в т.ч. без `is_navigator` — то различие вообще про
  тарифы). Доступен всем, кому виден раздел (выпустился ИЛИ админ) — не
  обязательно уже открытому тумблером: посмотреть, с кем можно будет говорить,
  когда откроют, не запрещено.
- `assert_torch_peer_visible(peer)` (`app/services/rooms.py`) — серверная
  сторона того же правила, вызывается вместо `contact_visible` при
  `torch=true` в `assert_peer_visible` (используется и при создании dm, и при
  `POST /api/rooms/{id}/members` — та смотрит на `room.torch_scope`
  существующей комнаты, а не на явный флаг из тела запроса).
- **Существующий (доэкспедиционный) dm с тем же собеседником** — `dm_key`
  уникален по паре, второй отдельной комнаты для того же пира внутри «Факела»
  завести нельзя. Открытие диалога из раздела **переводит** ту же комнату в
  `torch_scope=true` (только повышает, никогда не понижает обратно) — с этого
  момента она пропадает из списка Рубки и появляется в «Факеле», история не
  теряется.

## Исключение из «выпускник не пишет»

`assert_can_write` (`app/services/rooms.py`) закрывает запись во всей Рубке для
выпустившихся (`assert_not_graduated`) — но раздел «Факел» целиком (проверка
по `room.torch_scope`, не только по `is_torch`) из этого правила исключён: именно
выпуск открывает доступ к клубу, а не причина его закрыть. Кто именно внутри —
решает не `graduated_at`, а факт членства (`room_members`): для singleton-чата
его ставит только тумблер, для dm/групп раздела — обычное создание/приглашение
с кругом видимости выше.

## Пользовательские эндпоинты (`/api/torch`)

| Endpoint | Behavior |
|---|---|
| `GET /torch/stub` | Текст заглушки — виден любому, кому виден пункт меню (выпустился или админ) |
| `GET /torch/contacts` | Контакты для «начать чат»/«группа» внутри раздела: члены клуба + любые админы (см. «Круг видимости» выше) |

## Админка (`/admin/torch`)

| Endpoint | Behavior |
|---|---|
| `GET /admin/torch` | Только выпустившиеся не-админы: `user_id`/`username`/`display_name`/`torch_unlocked`, плюс текущий `stub_text` |
| `POST /admin/torch/grant` | `{user_ids}` — включить тумблер + добавить в комнату клуба (идемпотентно) |
| `DELETE /admin/torch/grant/{user_id}` | Выключить тумблер + убрать из комнаты |
| `PATCH /admin/torch/stub` | `{stub_text}` — обновить общий текст заглушки |

Фронтенд — `frontend/src/features/admin/AdminTorch.tsx` (прямая копия паттерна
`AdminSurvey.tsx`: поиск, чекбоксы, массовое действие) + текстовое поле для
заглушки над списком.

## Границы (не входит в эту задачу)

- Подписка/биллинг — гейт полностью ручной, проверки оплаты нет.
- Чаты по интересам (`can_create_groups`), анонсы доп. эфиров и сами эфиры —
  остаются на будущее.
- Стена с постами в профиле Аргонавта (ARG-155) — отдельная задача.
- Модерация чата — стандартные правила Рубки (soft-delete сообщений, админ
  удаляет любое), новых прав не вводили.
