# Протокол задачи

Контракт на то, как выглядит задача в Linear. Обязателен для всех проектов команды
`ArgonauticaPlatform`. Задача без протокола в работу не берётся — `/work` останавливается
и отправляет её через `/idea`.

**Источник правды — Linear.** Описание задачи живёт в Linear и нигде больше.
Репозиторий не хранит копий спек: `/idea` и `/slice` пишут в Linear, `/work` читает
оттуда же. Если спека и код разошлись — правда в Linear, а `docs/` обновляется в той же
задаче, что меняет поведение.

## Шаблон

```markdown
## Зачем

Какую проблему пользователя решаем. Одним абзацем, без решения — только боль.

## Что сделать

* Пунктами. Каждый пункт — проверяемое действие, а не направление мысли.

## Готово, когда

* Проверяемые критерии. «Кнопка появилась и открывает X», а не «стало удобнее».

## Границы

Что в эту задачу явно **не** входит. Самый важный раздел: именно его отсутствие
превращает мелкую правку в двухчасовую сессию.

## Как проверить

Конкретный сценарий, который агент прогоняет **перед** сдачей:
`make lint && make test`, плюс — для UI — путь кликов в Playwright,
плюс — при необходимости — проверка на staging.

## Assumptions

Решения, принятые агентом за пользователя, потому что ответ не менял бы объём работы.
Пусто — если таких не было.
```

Разделы «Зачем», «Что сделать», «Готово, когда», «Границы», «Как проверить» —
обязательны. «Assumptions» может отсутствовать.

## Калибратор размера

Правило: **одна задача — один контекст — один PR.** Если фича не влезает в один
контекст, она неправильно нарезана; это сигнал, что пропущен этап планирования,
а не ограничение инструмента.

Задача считается влезающей в один контекст, если выполнено **всё**:

| Проверка | Порог |
|---|---|
| Файлов затронуто | ≲ 8 |
| Миграций | ≤ 1 |
| Доменных доков из `docs/` нужно прочитать | ≤ 2 |
| Затронуто доменов (чат, KB, Задачи, Динамика, …) | 1 |
| PR можно прочитать целиком за один заход | да |

Не считается нарушением: вертикальный слайс, проходящий через миграцию → модель →
эндпоинт → экран, если он про **одну** сущность. Это как раз правильная форма.

Считается нарушением: горизонтальный пласт («все модели», «весь API раздела»,
«переписать все экраны») — такая задача не даёт проверяемого результата в одиночку.

Если хотя бы одна проверка не проходит → задача идёт в `/slice`, а не в `/work`.

## Правило допроса

`/idea` задаёт вопросы, но ограниченно.

- Вопрос задаётся **только** если разные ответы дают **разную работу**. Всё остальное —
  разумный дефолт + строка в «Assumptions».
- Не больше 4 вопросов за раунд, не больше 2 раундов. Если после двух раундов ясности
  нет — задача слишком крупная, её надо резать, а не доуточнять.
- Вопросы — про поведение продукта и границы, не про реализацию. «Что видит юзер, если
  файл не загрузился» — да. «Ставим индекс или нет» — нет, это решает исполнитель.
- Агент **спорит по существу**: если формулировка противоречива, конфликтует с
  `docs/DECISIONS.md` или задача явно больше, чем звучит — говорит об этом сразу,
  до заведения задачи, а не молча соглашается.

## Маршрут задачи

```
сырая мысль ──/idea──► задача в Linear по протоколу
                            │
                     калибратор размера
                            │
                ┌───────────┴───────────┐
            влезает                не влезает
                │                       │
             /work                   /slice ──► набор подзадач ──► /work
```

`/idea` и `/slice` кода не пишут вообще. `/work` не переформулирует задачу —
если по ходу выяснилось, что задача не та, он останавливается.

## Направления (проекты Linear)

| Проект | Домен |
|---|---|
| Security — кибербезопасность | авторизация, IDOR, секреты, аудит |
| Legal — юридический контур | оферта, персданные, платежи |
| Backend — документация и устойчивость | `docs/`, наблюдаемость, метрики, хранилище |
| Frontend и дизайн-система | React, токены, Figma, компоненты |
| UX и Product — подписка, путь, кураторы | путь пользователя, тарифы, продуктовые решения |
| INFRA — надёжность и доставка | Docker, nginx, деплой, MinIO, сеть |
| DevEx — процесс разработки | скиллы, тесты, CI, окружение агента |
