# /work — задача Linear → зелёный PR

Вход — идентификатор задачи (`ARG-NN`). Если его не дали — спроси, не начинай по устному
пересказу: устный пересказ уже один раз потерял границы, ради этого весь протокол
и существует.

Прочитай [docs/TASK_PROTOCOL.md](../../../docs/TASK_PROTOCOL.md) — шаблон и калибратор.
Правила репозитория (команды, `make`, миграции, git) — в `CLAUDE.md`, они здесь главнее.

## Шаг 0. Два гейта до начала работы

`mcp__linear__get_issue` с `includeRelations: true`. Затем:

**Гейт протокола.** Нет разделов «Границы» и «Готово, когда» → остановись. Скажи:
задача не по протоколу, нужен `/idea`. Не додумывай границы сам — именно это додумывание
и превращает правку в двухчасовую сессию.

**Гейт размера.** Прогони калибратор. Не влезает, или стоит `> Требуется нарезка`, или
есть незакрытые `blockedBy` → остановись. Скажи: сначала `/slice ARG-NN` (или сначала
блокирующая задача). Не начинай «хотя бы кусочек».

Оба гейта — жёсткие. Пройти их «под ответственность пользователя» можно только если он
прямо на этом настаивает после того, как ты сказал о риске.

## Шаг 1. Завести работу

1. Статус → `In Progress` (`mcp__linear__save_issue`, `state: "In Progress"`).
2. Выбери режим по правилам git из `CLAUDE.md`:
   - **fix** — багфикс, мелкий рефактор, текст/стиль → коммит прямо в `develop`;
   - **feature** — новая фича, миграция, кросс-модульное изменение → ветка
     `feature/<slug>` (можно взять `gitBranchName` из задачи) + PR в `develop`.
   Не уверен, куда попадает — считай feature. Лишняя ветка дешевле, чем прямой коммит
     в `develop` не глядя.
3. Прочитай **только** доки, названные калибратором (≤ 2 из индекса `CLAUDE.md`).
   Не читай `docs/` целиком. Если задача трогает что-то, что выглядит переусложнённым, —
   сначала `docs/DECISIONS.md`, там может быть 🔒.

## Шаг 2. Сделать — строго в границах

- Реализуй ровно «Что сделать». Всё, что попадает в «Границы», не трогай, даже если
  оно рядом и «на пять минут».
- Заметил проблему за границами — не чини. Дособери в список и предложи в конце
  завести через `/idea`.
- Для fix: сначала регрессионный тест, который **падает** до правки, потом правка
  (правило из `CLAUDE.md`).
- Новый эндпоинт → интеграционный тест против реального тестового DB/Redis, без моков.
- Меняешь поведение, описанное в `docs/` → правь соответствующий док **в этой же задаче**.

## Шаг 3. Проверка — только через CI

**Локально НИЧЕГО не запускать:** ни `make lint/test/local-up`, ни pytest/npm/tsc,
ни Playwright (см. «Verification = CI ONLY» в `CLAUDE.md`; хук и deny это блокируют).
Не обходи: ни raw-командами, ни `CI=true`, ни вторым worktree «для контроля».

Перед сдачей — только чтение: перечитай свой дифф на соответствие «Готово, когда»,
убедись, что регрессионный тест написан (для fix) и что `docs/` обновлены.

UI-задача: визуально локально не проверяется. Подготовь для отчёта список «что
посмотреть на staging» из раздела «Как проверить» (экраны, сценарий, краевые случаи).
Не пиши «работает» — пиши «UI не проверен визуально, проверить на staging».

## Шаг 4. Сдать: CI → (staging до мёржа) → мёрж → уборка

1. **Один** коммит в конце задачи. Conventional commits, по-русски в теле.
2. `git push`, PR в `develop`.
3. `gh pr checks <PR>`. Красный → `gh run view <run-id> --log-failed`, чини по логу,
   пушь новый коммит (дождись CI по новому sha). Падает тест, заведомо сломанный на
   develop, и диф этих областей не трогает — можно идти дальше, но скажи об этом в отчёте.
4. Дальше путь зависит от типа задачи.

### А. Проверяется только CI (инфра, тесты, рефакторинг, фикс без видимого поведения)

Зелёный CI → сразу мёрж (п. 5) → в Linear `Done`.

### Б. Меняет поведение или UI — проверка на staging ДО мёржа

Staging один и собирается из одной ветки за раз. Порядок такой:

1. **Раздел «Проверить на staging (вручную)»** с чекбоксами `- [ ]` (экран, шаги, краевые
   случаи) должен быть в описании задачи. Нет — добавь сам.
2. **Миграции в ветке?** `git diff --name-only origin/develop... -- backend/alembic/versions`.
   Есть — **сначала скажи человеку**, затем сделай дамп staging (см. «Дамп» ниже).
   Миграцию, уже выкаченную на staging, потом НЕ правь: нужна новая следующая миграция.
3. **Очередь.** Узнай, что сейчас на staging (Environments → staging на GitHub, или спроси).
   Там чужая ветка на проверке — не перетирай её, скажи человеку и жди своей очереди.
4. Выкати ветку: `gh workflow run deploy-staging.yml --ref <ветка>`; дождись окончания
   прогона (`gh run list --workflow=deploy-staging.yml --limit 1`).
5. Linear: статус → `На проверке` (уже ДО мёржа), комментарий: PR, что показал CI,
   «ветка на staging, жду ручной проверки». Сообщи человеку: https://staging.argonautica-systems.ru
   и список чекбоксов. **Остановись и жди.**
6. Человек нашёл баг → коммиты в ТУ ЖЕ ветку/PR, CI, пункт 4 заново. Закрытый PR
   «дополнять» нельзя, а этот ещё открыт — именно ради этого проверка идёт до мёржа.
7. Человек одобрил → мёрж (п. 5). После мёржа `develop` сам выкатится на staging — это и
   есть вторая проверка «всё вместе». Дамп удали сразу (см. «Дамп»). `Done` ставит
   человек, когда отметит все чекбоксы.

**Баг нашёлся уже ПОСЛЕ мёржа** (на выкатившемся `develop`): закрытый PR не трогаем и
не переоткрываем. Новая ветка из `develop` → короткий PR с **тем же `ARG-NN`**;
задача остаётся `На проверке`.

### Дамп staging (только если в ветке есть миграции)

Данные участников → дамп живёт только на сервере, в репозиторий и никуда больше не
копируется. Путь — вне каталога деплоя (`rsync --delete` стирает `/opt/platform-staging`).

```
# создать (БД небольшая, секунды)
ssh platform-new 'docker exec platform-staging-postgres-1 sh -c "pg_dump -U \$POSTGRES_USER \$POSTGRES_DB" | gzip > /root/staging-predeploy.sql.gz'
# удалить — как только дамп не нужен
ssh platform-new 'rm -f /root/staging-predeploy.sql.gz'
```

Удалять **сразу**: после мёржа и успешного передеплоя `develop`, либо когда ветку
бросили и staging снова здоров. Сообщи в отчёте, что дамп создан и что удалён.
Восстановление из дампа — только с явного подтверждения человека.

5. **Мёрж и уборка (обязательны, сразу после мёржа):**
   `gh pr merge <PR> --squash --delete-branch`, затем
   `git checkout develop && git pull --ff-only && git fetch --prune`.
   `gh pr merge` оставляет тебя на `main` — не коммить туда. Свой worktree (если был)
   удали: `git worktree remove <путь>`. `git branch --merged develop` — своих веток там
   быть не должно. `develop` и `main` защищены от удаления; на GitHub включено
   автоудаление веток после мёржа. `develop` → `main` не трогай никогда, это делает человек.
6. Если по ходу выяснилось, что задача больше, чем казалась — **не дожимай**.
   Останови работу, закоммить то, что закончено и зелено, опиши в комментарии к задаче,
   что осталось, и заведи продолжение отдельной задачей.

## Шаг 5. Отчитаться

Коротко: что сделано, чем проверено (результат CI, а не «должно работать»), что смотреть на staging (те же чекбоксы, что в задаче), что убрано за собой (ветки, worktree),
ссылка на PR, что осталось за границами и достойно отдельной задачи.

## Границы скилла

- Не переформулируешь задачу. Считаешь, что задача не о том → останавливаешься и
  отправляешь в `/idea`.
- Не режешь задачу сам по ходу дела → `/slice`.
- Не трогаешь `docker/docker-compose.prod.yml`, `docker/deploy.sh`, `.env`,
  `docker/nginx/certs/` — никогда.
- Не закрываешь задачу, если CI красный. Задачу с изменением поведения не переводишь в `Done` сам — только в `На проверке`, и фичу не вливаешь, пока человек не одобрил её на staging.
